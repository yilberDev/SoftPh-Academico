# HU-006 — Visualización de residentes registrados

> Transcripción de la Tabla 6 del documento académico (*PROYECTO DE GRADO*). El documento original no se modifica.

| Campo | Valor |
|---|---|
| Número | HU-006 |
| Nombre de la historia | Visualización de residentes registrados |
| Prioridad en el negocio | Alta |
| Programador responsable | Yilber Sanchez |
| Rol del usuario (Cómo) | Administrador, quiero visualizar la lista de residentes registrados en el sistema. |
| Deseo (Qué) | Acceder a una lista completa de residentes con sus datos relevantes. |
| Propósito (Para) | Gestionar y supervisar la información de los residentes de manera eficiente. |
| Observaciones | La administración debe poder consultar la información de los residentes registrados para facilitar su gestión y supervisión. |

## Criterios de aceptación

| No. | Contexto | No. | Evento |
|---|---|---|---|
| 1 | Listado de residentes | 1 | El sistema debe mostrar una tabla con al menos las siguientes columnas: nombre completo, número de documento, unidad donde reside, teléfono y correo electrónico. |
| | | 2 | La tabla debe ser paginable para manejar grandes cantidades de residentes. |
| 2 | Funciones de búsqueda y filtrado | 1 | El administrador debe poder buscar residentes por nombre o número de documento. |
| | | 2 | Debe haber opciones de filtrado por estado del residente, como activo o inactivo. |
| 3 | Interfaz amigable | 1 | La tabla debe ser visualmente clara y fácil de navegar, con posibilidad de ordenar las columnas por nombre, documento, unidad donde reside, entre otras. |
| | | 2 | Debe mostrar mensajes de carga o de ausencia de registro cuando no haya residentes registrados. |
| 4 | Actualización en tiempo real | 1 | Cualquier cambio realizado en la información de los residentes debe reflejarse en la lista visible. |
| | | 2 | El administrador debe recibir una confirmación de los cambios realizados. |

## Alcance

HU-006 es **solo de consulta**: no crea, edita ni elimina residentes (la gestión es HU-015). Solo para el ADMINISTRADOR. Ver [extensiones de diseño](../extensiones-diseno.md) (HU-006).

**Residente registrado (extensión de diseño, no modifica esta HU):** cuenta con rol `RESIDENTE`, no eliminada, con estado `ACTIVE` (se muestra "Activo") o `DISABLED` (se muestra "Inactivo") y con una relación residencial vigente (`resident_units` con `ended_at` vacío, creada al activar la cuenta en HU-019). Las cuentas `PENDING_ACTIVATION` (invitadas sin activar), las residencias terminadas y las cuentas eliminadas no forman parte del listado. Ver [extensiones de diseño](../extensiones-diseno.md) (HU-006).

## Estado de cumplimiento

- **Cumplidos:** criterio 1, criterio 2, criterio 3 y criterio 4.1.
- **Pendiente:** criterio 4.2, pendiente de reevaluación. Su dependencia, HU-015, está implementada desde el commit `faf73fd` (seguimiento del 2026-10-22); el criterio no se ha reevaluado todavía.

| Criterio | Estado | Detalle |
|---|---|---|
| 1.1 | Cumplido | `/admin/residents` muestra Nombre, Documento, Unidad (identificador de HU-013, p. ej. `B1-TO2-APTO-104`, derivado y nunca almacenado), Teléfono, Correo y Estado. |
| 1.2 | Cumplido | Paginación en el servidor (10, 25 o 50 por página; la API admite de 1 a 100), con "Mostrando 11–20 de 42 residentes", "Página X de Y", Anterior y Siguiente. |
| 2.1 | Cumplido | Búsqueda en el servidor por nombre (sin distinguir mayúsculas ni tildes) o documento, por fragmento; `%` y `_` se buscan literalmente. Se consulta al dejar de escribir (300 ms). |
| 2.2 | Cumplido | Filtro Estado: Todos, Activo, Inactivo. Combinable con la búsqueda. |
| 3.1 | Cumplido | Ordenamiento en el servidor por Nombre, Documento, Unidad, Teléfono, Correo y Estado, ascendente o descendente (clic en el encabezado). La unidad se ordena numéricamente por bloque, torre y apartamento; el documento numérico, como número; sin teléfono, al final. Las opciones quedan en la URL. Tabla adaptable a móviles (se desplaza dentro de su tarjeta). |
| 3.2 | Cumplido | Mensajes "Cargando residentes…", "Aún no hay residentes registrados." y "Ningún residente coincide con la búsqueda o el filtro."; error con "Reintentar". |
| 4.1 | Cumplido | La lista visible se mantiene al día **volviendo a consultar los datos** (refetch sin caché): al cambiar búsqueda, filtro, orden o página, al regresar a la vista o a la pestaña y con "Reintentar". Cada consulta lee el estado actual, así que refleja las activaciones (HU-019), las renumeraciones de bloque, torre o apartamento (HU-013) y los cambios en las cuentas. No hay actualización push: no se usan WebSockets, SSE ni conexiones persistentes. |
| 4.2 | Pendiente de reevaluación | HU-006 ya puede consultar de nuevo y mostrar los datos actualizados, pero la confirmación se produce después de una modificación de la información del residente, y esa operación (la edición del residente) pertenece a HU-015. HU-006 no crea operaciones de modificación. **Seguimiento (2026-10-22):** HU-015 está implementada (`faf73fd`): tras guardar, el detalle del residente muestra «Los datos del residente se actualizaron. El listado de residentes ya muestra la información nueva.» y, tras eliminar, el listado lo indica (`frontend/src/lib/residents/resident-detail.ts`; prueba `frontend/tests/resident-detail.test.ts`, sin E2E). Si esto cumple el criterio 4.2 de HU-006 queda pendiente de reevaluación; su estado no se cambia aquí. |
