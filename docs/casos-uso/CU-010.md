# CU-010 — Realizar pago electrónico

> Transcripción de la Tabla 54 del documento académico (*PROYECTO DE GRADO*, apartado 13.4.5 «Ficha de especificación de casos de uso»). El documento original no se modifica. El texto se transcribe literalmente, incluidos «3.Selecciona» y «4.Muestra» sin espacio, el paso 3 sin punto final, «1. Acceder» y «9. Registrar» en infinitivo, y «Post condición».

| Campo | Descripción |
|---|---|
| Identificador de Caso Uso | CU-010 |
| Nombre | Realizar pago electrónico |
| Descripción | Permite al residente iniciar un proceso de pago electrónico de sus obligaciones mediante una pasarela de pagos en un entorno de demostración, registrar el resultado de la transacción y actualizar el estado de su cuenta. |
| Actores | Residente |

## Secuencia normal

| Actor | Software |
|---|---|
| 1. Acceder a su estado de cuenta. | 2. Muestra las obligaciones pendientes disponibles para pago. |
| 3.Selecciona la obligación que desea pagar | 4.Muestra el valor correspondiente y las opciones para iniciar el pago. |
| 5. Inicia el proceso de pago electrónico. | 6. Inicia la transacción en el entorno de demostración. |
| 7. Completa el proceso de pago de prueba. | 8. Recibe y valida el resultado de la transacción. |
| | 9. Registrar el resultado del pago. |
| | 10. Actualiza el estado de cuenta del residente cuando la transacción es aprobada. |
| | 11. Genera el comprobante correspondiente. |
| | 12. Actualiza el historial de pagos del residente. |
| | 13. El caso de uso termina. |

## Excepciones

| Actor | Software |
|---|---|
| 3a. No tiene obligaciones disponibles para pago. | 4a. Informa que no existen obligaciones pendientes para realizar el pago. |
| 5a. Cancela el proceso antes de completarlo. | 6a. Cancela la operación y mantiene sin cambios el estado de la cuenta. |
| 7a. La transacción de demostración es rechazada. | 8a. Registra el resultado como rechazado e informa al residente que el pago no fue aplicado. |
| 7b. Se presenta un error durante el procesamiento. | 8b. Informa que no fue posible completar la transacción y conserva el estado anterior de la cuenta. |

## Nota técnica de implementación

> Esta nota no forma parte de la transcripción y no altera la secuencia ni las excepciones de la Tabla 54, que se conservan arriba literalmente. La correspondencia paso a paso está en [CU-010 frente a la implementación](../extensiones-diseno.md#cu-010-frente-a-la-implementación).

- **Pasos 1–6 (obligación, valor e inicio).** El residente abre `/resident/demo-payments`, elige una obligación pendiente y el monto, revisa la confirmación y pulsa «Iniciar pago de demostración». El software crea la transacción de demostración (`INITIATED`) y lleva al residente a su **checkout independiente**, `/resident/demo-payments/checkout?transaction=<id>`, que se recupera del servidor si se recarga.
- **Paso 7 (completar el pago de prueba).** En el checkout el residente **selecciona un instrumento de prueba ficticio** del catálogo que entrega el backend (tarjeta terminada en 0001, tarjeta terminada en 0002 o cuenta de prueba) y pulsa «Procesar pago de demostración». Solo se envía el identificador del instrumento.
- **Paso 8 (recibir y validar el resultado).** **El sistema, no el actor, determina la respuesta simulada**: el backend la resuelve a partir del instrumento y aplica sus reglas (vencimiento, elegibilidad, saldo) antes de fijar el estado final; la interfaz muestra una vista de procesamiento y después solo el estado que responde el servidor.
- **Pasos 9–12 (registro, saldo, comprobante e historial).** Si el resultado es una aprobación, se registran el pago y su aplicación a la obligación elegida, el saldo pendiente se recalcula y el recibo PDF de demostración queda disponible bajo demanda, desde el resultado del checkout y desde el detalle del pago en «Mis pagos». Los demás resultados no registran pagos.
- **Excepciones.** 5a/6a: «Cancelar operación», con confirmación, deja la transacción cancelada y vuelve a las obligaciones. 7a/8a: el instrumento de fondos insuficientes produce un rechazo simulado. 7b/8b: el instrumento de error técnico produce un error simulado; una aprobación que ya no puede aplicarse termina `FAILED` (`NOT_APPLIED`). Tras un rechazo o un error simulado, el residente puede iniciar una transacción nueva con otro instrumento.
- **Diferencia con la especificación.** En la Tabla 54 el resultado lo recibe el software desde la pasarela de demostración; en la implementación no hay pasarela externa: el actor elige el instrumento y el sistema determina la respuesta simulada. **La correspondencia académica de esta adaptación (criterio 2.2 de [HU-010](../historias-usuario/HU-010.md)) sigue pendiente de validación por el responsable académico.**
