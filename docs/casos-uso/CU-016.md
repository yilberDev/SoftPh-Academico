## Correspondencia con la implementación actual

> **Nota histórica (actualizada el 2026-10-10).** La descripción de esta sección se redactó como «caso de uso derivado» antes de localizar y transcribir la ficha oficial. Su nota original decía: «El documento académico nombra CU-016 en la matriz de trazabilidad (módulo *Autenticación*, actor Residente), pero no incluye su descripción detallada.» Esa afirmación ya no es vigente: el documento académico incluye la ficha de CU-016 en la Tabla 60, transcrita arriba (verificada en la auditoría de las fichas de casos de uso del 2026-10-10). La descripción se conserva como correspondencia con la implementación, no como parte de la ficha. Sigue la *Plantilla para descripción detallada de casos de uso* aprobada y aplica las decisiones registradas en [extensiones de diseño](../extensiones-diseno.md). No añade funcionalidades a HU-016 / RF-016. Solo para residentes.

### Diferencias con la ficha oficial

- **Nombre y actor:** coinciden (Restablecer contraseña; Residente).
- **Flujo principal:** la ficha es genérica (solicitar la información, validarla, establecer la contraseña e informar). La implementación lo hace con un **enlace de un solo uso enviado por correo** (paso 5), retira el código del enlace de la barra de direcciones, cambia la contraseña en una sola operación (Argon2id), cierra todas las sesiones y no inicia sesión.
- **Excepción 3a:** la ficha **informa** cuando la información no corresponde a una cuenta registrada («no fue posible iniciar el proceso de recuperación»). La implementación muestra **siempre el mismo mensaje** y no genera enlace ni envía correo, para no revelar si la cuenta existe. Es una diferencia de comportamiento deliberada, no una omisión. Esta diferencia está cubierta por la **interpretación de seguridad aprobada** del criterio 3 de [HU-016](../historias-usuario/HU-016.md#estado-de-cumplimiento) («Cumplido, con la interpretación de seguridad aprobada») y registrada en [extensiones de diseño](../extensiones-diseno.md#hu-016--restablecimiento-de-contraseña-del-residente-detalle) («Criterio 3 (anti-enumeración)»): el mensaje uniforme impide revelar si una cuenta existe. Por eso no se registra como una aceptación académica pendiente. La transcripción oficial de la Tabla 60, arriba, no cambia. 5a (contraseña inválida) está cubierta; 6b se describe en el punto siguiente. La implementación añade el límite de 3 enlaces por hora, el fallo del correo, el enlace inválido, vencido, usado o reemplazado y el uso simultáneo del mismo enlace.
- **Excepción 6b (error durante la actualización)** (verificado el 2026-10-10 por lectura del código y de las pruebas, sin ejecutarlas): la contraseña, los enlaces pendientes y las sesiones se actualizan en **una sola transacción atómica** (`confirm_reset` en `backend/app/services/password_reset.py`). Ante un error devuelto por el servidor o sin respuesta, la interfaz vuelve al formulario con un aviso (el mensaje del servidor o «No fue posible conectar con el servidor. Intenta de nuevo.») y permite reintentar (`frontend/src/lib/auth/password-reset.ts`). La prueba existente cubre el **fallo de red** («network failure: back to the form, can retry», `frontend/tests/password-reset.test.ts`); **no hay prueba de un fallo del servidor a mitad de la operación**, de modo que ese escenario solo está respaldado por la inspección del código.
- **Precondición y postcondición:** la ficha exige una cuenta **registrada**; la implementación, una cuenta **activa** (CU-019) y acceso al correo. La postcondición de la implementación añade el enlace usado, las sesiones cerradas y la auditoría.
- **Relaciones:** la ficha relaciona CU-007 y «CU-018 Controlar acceso según rol»; **la versión derivada no cita CU-018** (solo CU-007). Correspondencia en la implementación (verificado el 2026-10-10 por lectura del código y de las pruebas, sin ejecutarlas): el restablecimiento solo procede para una cuenta con rol `RESIDENTE` y estado `ACTIVE` (`backend/app/services/password_reset.py`); con otra cuenta no se genera enlace y la respuesta es la misma. Las rutas `POST /auth/password-reset/request`, `…/verify` y `…/confirm` son **públicas** en `ACCESS_POLICY` (`backend/tests/integration/test_access_control.py`), con `Origin` y el enlace de un solo uso, porque se usan sin sesión: «públicas» significa que no exigen una sesión ni un rol de sesión, **no** que cualquier rol pueda completar un restablecimiento válido. Al confirmar se cierran todas las sesiones del residente ([HU-018](../historias-usuario/HU-018.md)).

### Descripción derivada (implementación)

| Campo | Descripción |
|---|---|
| Identificador de caso de uso | CU-016 |
| Nombre | Restablecer contraseña |
| Descripción | Permite al residente que no puede acceder solicitar un enlace por correo, validar su identidad con ese enlace y establecer una contraseña nueva. |
| Actores | Residente. |

#### Secuencia normal

| Paso | Actor | Software |
|---|---|---|
| 1 | En la página de inicio de sesión selecciona "¿Olvidaste tu contraseña?". | |
| 2 | | Solicita el correo electrónico de la cuenta. |
| 3 | Ingresa su correo y confirma. | |
| 4 | | Muestra siempre el mismo mensaje: "Si la cuenta corresponde a un residente registrado, recibirás en tu correo un enlace para restablecer la contraseña. El enlace vence en 1 hora." |
| 5 | | Si el correo es de un residente activo: invalida cualquier enlace anterior, genera uno nuevo de un solo uso (guarda solo su resumen criptográfico), lo registra en la auditoría y lo envía por correo. |
| 6 | Abre el enlace recibido. | |
| 7 | | Retira el código del enlace de la barra de direcciones y verifica que el enlace siga vigente, sin usar y sin reemplazar, y que la cuenta siga activa. |
| 8 | | Muestra el formulario: nueva contraseña y confirmación. |
| 9 | Ingresa la nueva contraseña dos veces y confirma. | |
| 10 | | En una sola operación: guarda la contraseña protegida (Argon2id), marca el enlace como utilizado, cierra todas las sesiones abiertas del residente y lo registra en la auditoría. |
| 11 | | Confirma "Tu contraseña fue actualizada correctamente." y ofrece "Iniciar sesión". |
| 12 | | El caso de uso termina. El residente inicia sesión con la nueva contraseña (CU-007). |

#### Excepciones

| Paso | Software |
|---|---|
| 3 | Si el correo está vacío o no tiene un formato válido, lo indica y no envía la solicitud. |
| 5 | Si el correo no corresponde a un residente activo (inexistente, administrador, pendiente de activación, deshabilitado o eliminado), no genera enlace ni envía correo; el mensaje del paso 4 es el mismo. |
| 5 | Si el residente ya pidió 3 enlaces en la última hora, no genera otro ni envía correo; el mensaje del paso 4 es el mismo. |
| 5 | Si el correo no se puede enviar, el fallo queda registrado en la auditoría; el residente puede solicitar un enlace nuevo. |
| 7 | Si el enlace no es válido, venció, ya fue utilizado o fue reemplazado por uno más reciente, lo informa y ofrece solicitar uno nuevo. |
| 9 | Si la contraseña no cumple las condiciones (12 a 128 caracteres, no solo espacios, distinta del correo) o la confirmación no coincide, indica el campo a corregir y no cambia nada. |
| 10 | Si el mismo enlace se usa a la vez en dos lugares, solo un cambio se completa; el otro informa que el enlace ya fue utilizado. |
