# Extensiones de diseño aprobadas

Decisiones aprobadas que interpretan o precisan el documento académico y que aún no están reflejadas en él.

| HU afectadas | Decisión |
|---|---|
| HU-001 | No hay registro público de administradores; el primer administrador se crea con un mecanismo controlado del backend. |
| HU-002, HU-007, HU-018 | Una única interfaz de login; el backend determina el rol (`ADMINISTRADOR` / `RESIDENTE`). Ambas HU se cumplen con el mismo flujo. |
| HU-005 | Gestión de feedback por el administrador: estados `PENDING`/`RESOLVED`, respuesta al residente separada de la nota interna de resolución, notificación por el correo existente, historial desde `audit_logs`, búsqueda por residente o asunto y bloqueo optimista con `version`. Ver detalle. |
| HU-004 | Registro manual de pagos: `charges`, `payments` y `payment_allocations` como fuente de verdad; aplicación FIFO; excedente como saldo a favor; el backend decide la unidad; recibo PDF y correo después de confirmar el pago. Ver detalle. |
| HU-006 | Solo consulta para el administrador. Se precisa qué es un residente registrado (`RESIDENTE`, no eliminado, `ACTIVE` = Activo o `DISABLED` = Inactivo, con residencia vigente) y que la lista refleja los cambios volviendo a consultar los datos (sin WebSockets, SSE ni actualización push). La confirmación de cambios (criterio 4.2) queda pendiente de HU-015. Ver detalle. |
| HU-018 | El control de acceso reutiliza la sesión y las dependencias de HU-002/HU-007 (sin tablas de permisos ni roles nuevos) y declara la política de cada endpoint. Ver detalle. |
| HU-004, HU-008, HU-011, HU-012, HU-014 | Las cuotas/cargos mensuales forman parte del modelo financiero; los saldos se calculan a partir de cargos y pagos. |
| HU-010 | El "pago electrónico demo/sandbox" se implementa como una simulación interna del backend, sin pasarela externa. |
| HU-017 y demás HU con notificaciones | Correo solo en los flujos definidos por los requisitos; Mailpit en desarrollo. |
| HU-003, HU-019, HU-007 | El administrador registra e invita (HU-003); el residente activa su cuenta con el enlace (HU-019); el residente inicia sesión con el login único (HU-007). Ver detalle. |
| HU-013 | Una única copropiedad (Urbanización San Joaquín) con la estructura física Bloque → Torre → Apartamento; la unidad residencial es el apartamento y su número es único dentro de su torre (ver detalle). |

## HU-001 — Registro de administrador (detalle)

| Tema | Decisión |
|---|---|
| Mecanismo | El "formulario de registro" de HU-001 se implementa como el comando interactivo `python -m app.cli create-admin`, que se ejecuta en el servidor. No existe endpoint HTTP ni página de registro. El comando cumple los tres criterios de aceptación: confirma el registro exitoso, rechaza correos ya registrados y muestra las validaciones incumplidas. |
| Alcance | El comando solo crea el **primer** administrador: si ya existe un administrador activo, rechaza la operación. |
| Datos | Obligatorios: nombre completo, correo electrónico y contraseña. Opcionales: número de documento y teléfono. |
| Correo solo ASCII (nuevos registros) | Desde la corrección de seguridad A-1, el correo de una cuenta nueva solo puede contener caracteres ASCII (sin tildes, eñes ni caracteres de ancho completo). Evita cuentas con correos visualmente parecidos a otros (homógrafos Unicode). Endurece la regla de validación de HU-001; el inicio de sesión no rechaza correos Unicode, simplemente no coinciden con ninguna cuenta. |
| Contraseña | Entre 12 y 128 caracteres, no solo espacios, distinta del correo, igual a la confirmación. Sin clases de caracteres obligatorias. Se guarda con Argon2id. |
| CU-001 | El documento no incluye la descripción detallada de CU-001; se redactó en [casos-uso/CU-001.md](casos-uso/CU-001.md) siguiendo la plantilla aprobada, sin funcionalidades adicionales. |
| Auditoría | La creación se registra en `audit_logs` (`ADMIN_CREATED`, origen `cli`). |
| Garantía ante concurrencia | La base de datos garantiza que exista como máximo un administrador activo: la columna generada `active_administrator_marker` vale 1 solo para un administrador activo y no eliminado (NULL en los demás casos), y el índice `UNIQUE` `uq_users_active_administrator_marker` admite un único 1. Si dos ejecuciones simultáneas del comando pasan la verificación previa, MySQL rechaza la segunda inserción y el comando informa que ya existe un administrador activo (migración `925c4947c7a3`). Reactivar un administrador deshabilitado mientras otro está activo también se rechaza. |

## HU-002 — Inicio de sesión del administrador (detalle)

| Tema | Decisión |
|---|---|
| Login único | `POST /api/v1/auth/login` es el único inicio de sesión para todos los roles y el backend determina el rol. Desde HU-007 admite ADMINISTRADOR y RESIDENTE (ver HU-007). |
| Respuesta indistinguible | Correo inexistente, contraseña incorrecta, cuenta deshabilitada, pendiente de activación o eliminada, y rol no permitido responden igual: 401 "Correo electrónico o contraseña no válidos.". Si el correo no existe se verifica contra un hash ficticio para igualar el tiempo de respuesta. El motivo real solo queda en `audit_logs`. |
| Sesión | Guardada en la tabla `sessions`. La cookie `softph_session` (HttpOnly, SameSite=Lax, Path=/, Secure configurable) contiene solo un token aleatorio de 256 bits; la base de datos guarda solo su SHA-256. Vence a las 8 horas o tras 30 minutos de inactividad (configurable en `.env`). Un nuevo login revoca la sesión previa de la cookie. Deshabilitar o eliminar la cuenta invalida sus sesiones. |
| CSRF | Token derivado: HMAC-SHA256 del token de sesión (no se almacena). Se exige junto con la comprobación de `Origin` en las modificaciones con sesión (hoy, el logout). El login solo exige `Origin`. |
| Control de intentos (criterio 3) | 5 fallos en 15 minutos bloquean el correo normalizado durante 15 minutos (configurable). El contador se guarda por hash del correo, exista o no la cuenta, así el bloqueo no revela qué correos están registrados. Los intentos del mismo correo se serializan con un bloqueo de fila, de modo que los intentos concurrentes se cuentan todos. Consecuencia aceptada: un tercero que conozca el correo puede bloquear temporalmente el acceso. |
| **Criterio 3 — pendiente** | **"Solicitará el restablecimiento de la contraseña" no está implementado.** No existe un flujo de restablecimiento para el administrador (HU-016 es del residente) y su implementación está aplazada. HU-002 no se considera completamente satisfecha hasta cubrirlo. |
| Panel principal | `/admin` es un panel mínimo de validación (saludo y cierre de sesión), sin funcionalidades de administración. |
| Protección de rutas (base de HU-018) | `get_current_auth` y `require_roles` (FastAPI) y el middleware SSR de Astro protegen `/admin`. HU-018 los reutiliza sin cambios y declara la política de cada ruta (ver HU-018). |
| IP en auditoría | Se registra `request.client.host`; no se confía en `X-Forwarded-For` hasta definir el proxy de producción. Detrás del proxy de desarrollo la IP registrada es `127.0.0.1`. |

## Correcciones de seguridad de HU-002 (A-1, M-1, M-2)

| Tema | Decisión |
|---|---|
| Identidad del correo: canonicalización de aplicación | La regla es `normalize_email()` (`backend/app/core/emails.py`): quitar espacios de los extremos (`strip`, que incluye tabuladores y espacios Unicode), normalizar a **NFC** y pasar a **minúsculas**. Se aplica antes de guardar, de buscar y de calcular el identificador del control de intentos. Son el mismo correo: mayúsculas/minúsculas, espacios en los extremos y formas Unicode compuesta/descompuesta (é = e + ◌́). Son correos distintos: con o sin tilde, de ancho completo (ＡＢＣ), `ı` sin punto y espacios internos. |
| Identidad del correo: base de datos | `users.email` compara byte a byte (`utf8mb4_0900_bin`, NO PAD). Antes usaba `utf8mb4_0900_ai_ci`, que igualaba variantes con tilde o de ancho completo y permitía eludir el bloqueo de intentos. MySQL y el control de intentos consideran ahora "el mismo correo" exactamente lo mismo. El identificador del contador se calcula siempre con el correo enviado por el cliente, nunca con el guardado. |
| CHECK de la base de datos | `ck_users_email_canonical` (`email = LOWER(email) AND email = TRIM(email)`) y `ck_users_email_ascii` (un byte por carácter) son una **defensa adicional, no un sustituto** de `normalize_email()`: MySQL no normaliza NFC, y `TRIM()` solo quita el espacio U+0020, no reproduce `strip()` de Python. |
| Migración `6236c5b88ac2` | Valida antes de modificar la estructura y aplica el cambio en una única sentencia `ALTER TABLE` (atómica en InnoDB). El `upgrade` aborta sin cambios si algún correo no es canónico o no es ASCII (no los reescribe, para no fusionar identidades). El `downgrade` aborta sin cambios si algún correo quedaría duplicado bajo `utf8mb4_0900_ai_ci` o si faltan las CHECK; solo después elimina las CHECK y restaura la colación, en la misma sentencia. |
| Argon2 fuera del bucle de eventos (M-1) | Verificar y calcular hashes Argon2 (64 MiB y ~65 ms cada uno) se ejecuta en hilos (`anyio.to_thread.run_sync`) con un `CapacityLimiter` de `PASSWORD_HASH_MAX_CONCURRENCY` operaciones simultáneas (por defecto 2, rango 1–4). El hash ficticio del login se calcula al arrancar la API. El comportamiento funcional no cambia. |
| Cookie `Secure` obligatoria fuera de local (M-2) | `SESSION_COOKIE_SECURE=false` solo se admite con `APP_ENV` `development` o `test` y `APP_ORIGIN` `http://localhost`, `http://127.0.0.1` o `http://[::1]`. En cualquier otro caso, y siempre con `APP_ENV=production`, la API y el comando `create-admin` no arrancan. El mensaje de error no muestra valores de configuración. |

## HU-013 — Gestión de unidades residenciales (detalle)

| Tema | Decisión |
|---|---|
| Estructura del dominio | La Urbanización San Joaquín se organiza en **Bloque → Torre → Apartamento**. Bloques y torres no aparecen en el documento académico: son la estructura necesaria para registrar correctamente las unidades. No se crean HU nuevas ni se cambian los criterios. La unidad residencial de HU-013 es el **apartamento** (tabla `units`; en la interfaz, "Apartamento"). |
| Nomenclatura | Bloques `B1`, `B2`…; torres `TO1`, `TO2`…; apartamentos `APTO-1`, `APTO-104`… Identificador oficial completo: **`B1-TO2-APTO-104`**. |
| Persistencia | Cada nivel guarda solo su número entero (`blocks.number`, `towers.number`, `units.number`). El identificador completo **no se almacena**: el backend lo deriva siempre de la jerarquía guardada (`app/core/unit_labels.py`) y la API lo devuelve en `label` (y el nombre del nivel en `name`). Todas las relaciones usan ids estables. |
| Sin rangos de negocio | Los números son enteros positivos, sin máximo de dominio. La columna `INT UNSIGNED` tiene un límite técnico (4 294 967 295) que se informa como "demasiado grande para el sistema", no como regla del negocio. |
| Unicidad | Un bloque activo por número; una torre activa por número dentro de su bloque (`TO2` puede existir en `B1` y en `B2`); un apartamento activo por número dentro de su torre. La garantía final son índices `UNIQUE` sobre columnas generadas `VIRTUAL` (`active_number_marker`: el número mientras no está eliminado, NULL después). |
| Edición | Se puede corregir el número de un bloque, una torre o un apartamento; si el nuevo número ya existe en su contexto, se rechaza (409). `block_id` y `tower_id` son inmutables: no existe un flujo de traslado. Control optimista con `version` (también en el borrado). Al renumerar un padre no se reescribe ninguna fila: solo cambia el identificador derivado de sus descendientes (`B1-TO2-APTO-104` → `B4-TO2-APTO-104`). La interfaz lo advierte antes de confirmar. |
| Borrado | Lógico (`deleted_at`), sin cascadas. Un bloque con torres activas o una torre con apartamentos activos no se puede eliminar (409). Una entidad eliminada no aparece en los listados y responde 404. Su número se puede reutilizar (nuevo registro con otro id). Restaurar queda fuera del alcance. Las claves foráneas usan `ON DELETE RESTRICT`. |
| Concurrencia | Orden fijo de bloqueos bloque → torre → apartamento con lecturas con bloqueo. Crear un hijo bloquea el padre en modo compartido; eliminar un padre lo bloquea en exclusiva y busca hijos activos, de modo que nunca queda un hijo activo bajo un padre eliminado. Los duplicados simultáneos los rechaza el `UNIQUE`. |
| Vista previa en formularios | La API entrega `child_label_prefix` (p. ej., `B1-TO2-APTO-`) y el formulario muestra ese prefijo + el número escrito. Es solo una vista previa: el identificador oficial es el `label` que devuelve el backend al guardar. |
| Búsqueda y paginación | No forman parte de HU-013. La interfaz usa navegación jerárquica con migas de pan (`Bloques › B1 › TO2`). |
| API | `GET`/`POST /api/v1/blocks`; `GET`/`PATCH`/`DELETE /api/v1/blocks/{id}`; `GET`/`POST /api/v1/blocks/{block_id}/towers`; `GET`/`PATCH`/`DELETE /api/v1/towers/{id}`; `GET`/`POST /api/v1/towers/{tower_id}/units`; `GET`/`PATCH`/`DELETE /api/v1/units/{id}`. Todas exigen sesión de ADMINISTRADOR; las modificaciones exigen además `Origin` y token CSRF. `DELETE` recibe `?version=`. |
| Auditoría | `BLOCK_CREATED`/`BLOCK_UPDATED`/`BLOCK_DELETED`, `TOWER_*` y `UNIT_*` en `audit_logs`, en la misma transacción, con el número y el identificador (anterior y nuevo en las ediciones). |
| Migración `522bf629af33` | Escrita a mano (Alembic no compara CHECK y solo maneja en parte las columnas generadas); la estructura real se verifica en `information_schema` en las pruebas. El `upgrade` aborta sin cambios si alguna de las tablas ya existe. El `downgrade` aborta sin cambios si hay filas (incluidas las eliminadas lógicamente) y luego borra las tres tablas en una sola sentencia atómica. |
| Relación con HU futuras | HU-003 implementó la disponibilidad de unidades (`/units/available`) y el rechazo del borrado de un apartamento en uso (409 `UNIT_IN_USE`). Residentes, cargos y pagos referencian `units.id`. Los documentos emitidos (p. ej., recibos) deberán guardar una copia del identificador vigente al emitirse; lo decidirá la HU correspondiente. |

## HU-003 — Registro de un residente mediante invitación (detalle)

| Tema | Decisión |
|---|---|
| Reparto HU-003 / HU-019 (T-1) | HU-003 implementa **solo el flujo del administrador**: formulario, apartamentos disponibles, usuario pendiente, invitación, reserva, correo y auditoría. **No** implementa `verify`, `activate`, la página `/activate-account`, la contraseña del residente, la residencia ni el login del residente: son de HU-019. El enlace del correo apunta a `/activate-account`, implementada en HU-019. |
| Vigencia | De 1 a 30 días (criterio 1.4 de HU-019, necesario al crear la invitación); 7 por defecto en el formulario (E-2). `expires_at = creación + vigencia`. Una invitación es vigente estrictamente antes de `expires_at` (UTC). |
| Disponibilidad (U-2) | Un apartamento está disponible si está activo (y su torre y bloque también), no tiene residencia activa y no tiene una invitación `PENDING` vigente. Un residente activo por apartamento y un apartamento activo por residente. La regla vive en el backend (`GET /api/v1/units/available` y otra comprobación al crear); el cliente solo envía `unit_id`. Las consultas (GET) no escriben: una invitación pendiente vencida simplemente deja de reservar y se marca `EXPIRED` cuando se detecta al procesar una creación o un reenvío. |
| Usuario (R-1, R-2) | Se crea al invitar: rol RESIDENTE, `PENDING_ACTIVATION`, sin contraseña, con el correo y el nombre que indica el administrador. El documento y el teléfono los aportará el residente en HU-019. |
| Correo existente | Administrador, residente activo, deshabilitado o eliminado → 409 `EMAIL_ALREADY_REGISTERED` (la misma regla de HU-001). Residente pendiente con invitación vigente → 409 `INVITATION_ALREADY_PENDING`. |
| Reinvitación (R-3) | Si el residente pendiente no tiene invitación vigente (la anterior venció), se crea una **invitación nueva** para el **mismo usuario**, con token y vigencia nuevos y el apartamento elegido en el formulario (el mismo u otro disponible). La invitación vencida queda `EXPIRED` y no se modifica. Si el administrador escribe otro nombre, se actualiza el del usuario pendiente (`full_name_updated` en la auditoría). |
| Normalización del correo (N-B) | `normalize_email(x) = NFC(lower(NFC(strip(x))))`, la única función autorizada (`app/core/emails.py`), igual que en HU-001 y HU-002. El correo del residente se valida con las mismas reglas que el del administrador (ASCII, formato), mediante validadores compartidos. |
| Token y enlace | 256 bits aleatorios (`generate_session_token`); en la BD solo se guarda `SHA-256` (`token_hash` UNIQUE). El token nunca se registra en logs, excepciones, auditoría ni respuestas. Va en el **fragmento** del enlace: `APP_ORIGIN/activate-account#token=…`, nunca en `?token=`. |
| Envío del correo (E-1) | T1 (validar, bloquear, crear el usuario y la invitación con `delivery_status = PENDING`, auditar `RESIDENT_INVITED`, COMMIT) → SMTP **sin transacción ni bloqueos abiertos** → T2 (`SENT`/`FAILED`, `send_attempts + 1`, `last_sent_at`, auditar `INVITATION_EMAIL_SENT`/`INVITATION_EMAIL_FAILED`, COMMIT). Un fallo SMTP no deja invitaciones huérfanas: la invitación sigue válida y se puede reenviar. Si falla T2, el envío queda "sin confirmar" (`PENDING`) y también se puede reenviar. |
| Reenvío (E-1, E-1c) | `POST /resident-invitations/{id}/resend`: solo una invitación `PENDING` y vigente. Bloquea la fila, genera un token nuevo (el enlace anterior deja de valer), mantiene el usuario, el apartamento y `expires_at` (no amplía la vigencia), audita `INVITATION_RESENT` y luego SMTP + T2. Los reenvíos simultáneos se procesan en serie y vale el último token. El resultado de un correo con un enlace ya rotado no sobrescribe el estado de envío vigente. |
| Lista de pendientes (E-1b) | `GET /resident-invitations?status=PENDING`: invitaciones vigentes con correo, nombre, apartamento, vencimiento, estado de envío e intentos, para reenviar cuando el correo falló. Nunca incluye el token ni su hash. |
| Estados | Invitación: `PENDING → USED` (HU-019) y `PENDING → EXPIRED`; nunca vuelve a `PENDING` (cada cambio de estado se condiciona a `status = 'PENDING'`). Envío: `PENDING`/`SENT`/`FAILED`. |
| Concurrencia | Orden de bloqueos apartamento → usuario → invitación (→ residencia en HU-019). La creación cierra antes la transacción de lectura de la sesión, para que sus lecturas vean todo lo confirmado antes del bloqueo del apartamento. El usuario existente se bloquea por id (nunca con una lectura con bloqueo sobre un correo inexistente, que provocaría interbloqueos). Garantía final en MySQL: `UNIQUE` sobre columnas generadas `VIRTUAL` (una invitación pendiente por apartamento y por usuario; una residencia activa por apartamento y por residente) y `uq_users_email`. |
| Integración con HU-013 | Un apartamento con residente activo o invitación vigente no se puede eliminar: 409 `UNIT_IN_USE` (el diálogo de borrado lo muestra como estado informativo). |
| Correo en desarrollo | `smtplib` de la biblioteca estándar en un hilo, con tiempo límite (`SMTP_TIMEOUT_SECONDS`), hacia Mailpit (`127.0.0.1:1025`, interfaz en `http://localhost:8025`). Sin dependencias nuevas. Nunca se envía correo real desde desarrollo. TLS y credenciales para un SMTP de producción quedan para el despliegue (E-3). |
| Auditoría | `RESIDENT_INVITED` (entidad `user`; `invitation_id`, `unit_id`, `validity_days`, `reinvitation` y, si aplica, `expired_invitation_ids` y `full_name_updated`), `INVITATION_EMAIL_SENT` / `INVITATION_EMAIL_FAILED` (entidad `resident_invitation`; `invitation_id`, `attempt` y el tipo de error) e `INVITATION_RESENT` (`invitation_id`, `unit_id`). Nunca el token, su hash ni el cuerpo del correo. |
| Migración `4cfaeb7a0be8` | Crea `resident_invitations` y `resident_units` (esta última solo la escribirá HU-019). Escrita a mano; la estructura real se verifica en `information_schema`. Las FK usan `ON DELETE RESTRICT` con índice propio. El `upgrade` aborta sin cambios si alguna tabla ya existe; el `downgrade` aborta sin cambios si hay filas y borra las dos tablas en una sola sentencia atómica. |
| Logs de Alembic en las pruebas | `alembic/env.py` llama a `fileConfig(..., disable_existing_loggers=False)`: antes, ejecutar las migraciones dentro del proceso de pruebas desactivaba los loggers de la aplicación, y la comprobación "el token no aparece en los logs" no habría comprobado nada. |

## HU-019 — Invitación y activación de cuenta del residente (detalle)

| Tema | Decisión |
|---|---|
| Reparto (T-1) | **HU-003 = invitación** (administrador), **HU-019 = activación** (residente), **HU-007 = inicio de sesión del residente**. Los criterios 1 a 3 de HU-019 (formulario, validación y enlace único) describen la parte del administrador y se cumplen con HU-003. HU-019 no crea invitaciones, no envía correos y no crea usuarios. |
| Criterio 6 y HU-007 (L-1) | La activación deja la cuenta `ACTIVE` y **no crea sesión**: el residente inicia sesión con el login único, habilitado para residentes en HU-007. Así, "permitirle iniciar sesión" (6.2) se cumple con HU-007; la pantalla final de la activación enlaza al login. |
| Sin migración | `resident_invitations`, `resident_units` y `users` (migraciones `633f6e19d008` y `4cfaeb7a0be8`) ya tienen todo lo necesario (`used_at`, CHECK `USED ⇔ used_at`, `document_number` UNIQUE, CHECK `active_has_password`, marcadores de residencia activa). Las acciones de auditoría nuevas no cambian el esquema (`audit_logs.action` es texto libre). |
| Página `/activate-account` | Pública. Lee `#token=` del fragmento, lo **retira de inmediato** de la barra de direcciones con `history.replaceState` (también si es inválido) y lo conserva solo en memoria: nunca en `localStorage`, `sessionStorage`, cookies ni en el HTML (el servidor nunca lo recibe en la URL). Cabeceras `Cache-Control: no-store` y `Referrer-Policy: no-referrer`. Estados: verificando, válida (datos de la invitación no editables + formulario), inválida, vencida, utilizada, activando, activada y error. |
| Endpoints públicos | `POST /api/v1/resident-invitations/verify {token}` y `POST /api/v1/resident-invitations/activate {token, document_number, phone, password, password_confirmation}`. Sin sesión y sin token CSRF (no hay sesión): exigen `Origin` (todo el router) y el token de un solo uso **solo en el cuerpo**. `extra="forbid"`: no aceptan `user_id`, `unit_id`, `invitation_id` ni `email`; usuario y apartamento salen siempre de la invitación encontrada por `SHA-256(token)`. Respuestas con `no-store`; `verify` devuelve solo `email`, `full_name`, `unit_code` y `expires_at`. |
| Respuestas | Token inexistente, alterado, mal formado (no se busca en la BD), reemplazado por un reenvío o de una cuenta que ya no está pendiente → 404 `INVITATION_INVALID` (la misma respuesta, sin pistas). Vencida → 410 `INVITATION_EXPIRED`. Utilizada → 410 `INVITATION_USED`. Documento registrado → 409 `DOCUMENT_ALREADY_REGISTERED`. Apartamento ocupado → 409 `UNIT_NOT_AVAILABLE`. Datos inválidos → 422 con detalle por campo. Origin inválido → 403 `CSRF_FAILED`. |
| Datos del residente (R-2) | Documento obligatorio y teléfono opcional, con los validadores de HU-001 (ahora funciones compartidas, sin cambio de comportamiento). Contraseña con la política de HU-001 (12–128, no solo espacios, distinta del correo, confirmación); "distinta del correo" se comprueba en el servicio con el correo de la invitación. Argon2id con `hash_password_async` (fuera del bucle de eventos, M-1). |

## HU-016 — Restablecimiento de contraseña del residente (detalle)

| Tema | Decisión |
|---|---|
| Alcance | **Solo residentes** (`RESIDENTE`, `ACTIVE`, no eliminado). No hay recuperación para el administrador: el criterio 3 de HU-002 sigue pendiente. Se entra desde el login de HU-007 ("¿Olvidaste tu contraseña?") y se vuelve a él tras el cambio. |
| Criterio 3 (anti-enumeración) | El documento pide informar que "la información proporcionada no corresponde a una cuenta válida". Para no revelar qué correos están registrados, la solicitud responde **siempre igual** (202, mismo cuerpo y cabeceras): "Si la cuenta corresponde a un residente registrado, recibirás…". | Endpoints públicos | `POST /api/v1/auth/password-reset/request {email}`, `…/verify {token}` y `…/confirm {token, password, password_confirmation}`. | Token | 256 bits (`generate_session_token`); en `password_reset_tokens` solo `SHA-256` (`token_hash` UNIQUE). Vigencia **1 hora**, un solo uso (`used_at`), revocable (`revoked_at`). El enlace es `/reset-password#token=…` (fragmento). Un token mal formado, inexistente o de una cuenta que dejó de ser válida → 404 `PASSWORD_RESET_INVALID`; vencido, usado o revocado → 410 `PASSWORD_RESET_EXPIRED` / `_USED` / `_REVOKED`. Solo quien tiene el token ve esas diferencias. |
| Una recuperación vigente | Cada solicitud revoca los enlaces pendientes del residente antes de crear el nuevo: el anterior deja de funcionar de inmediato. MySQL lo garantiza con un `UNIQUE` sobre la columna generada `pending_user_marker` (user_id mientras no está usado ni revocado). |
| Límite de solicitudes | 3 enlaces por residente por hora (cuenta los tokens creados en la última hora, bajo el bloqueo de la fila del usuario, así que es exacto con solicitudes simultáneas). Al superarlo se responde igual (nunca 429, que delataría la cuenta) y no se crea enlace ni se envía correo; queda `PASSWORD_RESET_REJECTED` (`rate_limited`) en la auditoría. Para correos que no son de un residente no se escribe nada. El control de intentos del login no cambia. |
| Correo en segundo plano | La respuesta sale antes del SMTP: el token se confirma en la BD y el correo se envía en una tarea en segundo plano de FastAPI (`BackgroundTasks`, sin dependencias nuevas), así el tiempo de respuesta no delata si el correo es de un residente. Un fallo de envío se audita como `PASSWORD_RESET_EMAIL_FAILED` (solo el tipo de error); el residente puede pedir otro enlace. Mailpit en desarrollo. |
| Cambio de contraseña | Política de HU-001 (validadores compartidos; "distinta del correo" se comprueba con el correo de la cuenta del token). Argon2id con `hash_password_async`, calculado sin transacción ni bloqueos abiertos. Luego una transacción atómica bloquea **usuario → token** (el mismo orden que la solicitud, para que no haya interbloqueos), revalida todo y: guarda el hash, marca el token `used_at`, revoca los demás pendientes y **revoca todas las sesiones** del residente; `PASSWORD_RESET_COMPLETED`. No crea sesión: el residente inicia sesión de nuevo. |
| Login y reset simultáneos | El login (HU-002/HU-007) ahora bloquea la fila del usuario (por clave primaria) antes de verificar la contraseña. Así un login y un reset del mismo usuario van en serie: o el reset revoca la sesión recién creada, o el login ya ve la contraseña nueva. Sin cambios en el contrato, los mensajes ni el control de intentos. |
| Bloqueo del login tras el reset | El reset no borra el bloqueo temporal del login (5 fallos → 15 min): hacerlo dentro de la misma transacción podría interbloquearse con un login en curso. Si el residente estaba bloqueado, podrá entrar con la contraseña nueva cuando venza el bloqueo (máximo 15 minutos). |
| Auditoría | `PASSWORD_RESET_REQUESTED` (`{reset_id}`), `PASSWORD_RESET_EMAIL_FAILED` (`{reset_id, error}`), `PASSWORD_RESET_REJECTED` (motivo seguro: `not_eligible`, `rate_limited`, `invalid`, `expired`, `used`, `revoked`, `user_not_eligible`) y `PASSWORD_RESET_COMPLETED` (`{reset_id, sessions_revoked}`). Nunca el token, su hash ni contraseñas. Los correos desconocidos no se auditan. |
| Página `/reset-password` | Pública, `Cache-Control: no-store` y `Referrer-Policy: no-referrer`. Lee `#token=` del fragmento (solo de un fragmento, nunca de la consulta), lo retira de inmediato con `history.replaceState` y lo mantiene solo en memoria. Estados: verificando, válido (formulario), inválido, vencido, utilizado, reemplazado, actualizando, completado y error. |
| Migración `b1b38cfb7fe2` | Crea `password_reset_tokens` (FK `RESTRICT` a `users`, índice `(user_id, created_at)` para la FK y el límite, CHECK `expires_at > created_at` y "usado o revocado, no ambos"). Escrita a mano; verificada en `information_schema`. El `downgrade` aborta si hay filas. |

## HU-004 — Registro de pagos de residentes (detalle)

Decisiones aprobadas para la implementación (D1–D8) e interpretaciones técnicas del requisito. Ninguna está escrita literalmente en la HU académica.

| Tema | Decisión |
|---|---|
| D1. Fuente de verdad | `charges` (obligaciones de una **unidad**, nunca de un usuario), `payments` y `payment_allocations` (cuánto de cada pago cubre cada cargo). Los saldos **no se almacenan**: pendiente = cargos − aplicaciones a ellos; saldo a favor = pagos − aplicaciones de ellos. HU-004 no genera cargos (mensualidades y mora llegarán con su HU); las pruebas los insertan de forma controlada. |
| D2. FIFO | El pago cubre automáticamente los cargos pendientes de la unidad en orden `due_date`, `created_at`, `id` (ascendente), sin importar el concepto del cargo. El concepto del pago describe el pago (aparece en el recibo); no elige a qué cargo se aplica. |
| D3. Saldo a favor | Lo que el pago no puede aplicar queda como saldo a favor del pago (derivado, no almacenado); nunca se pierde. Usar ese saldo en cargos posteriores no es parte de HU-004. |
| D4. Métodos | `CASH` (Efectivo), `CARD` (Tarjeta), `TRANSFER` (Transferencia). Ningún otro (CHECK en la base de datos). |
| D5. Conceptos | `MONTHLY_FEE` (Mensualidad), `LATE_FEE` (Mora), `PENALTY` (Penalización), `OTHER` (Otro). «Otro» exige descripción (hasta 200 caracteres) y los demás no la admiten. |
| D6. Fechas | `payment_date` (fecha en que se pagó; calendario de Bogotá; nunca posterior a hoy en Bogotá; no anterior al 1 de enero de 2000, límite técnico) y `registered_at` (fecha y hora de registro, UTC, la pone el servidor). |
| D7. Recibo después del COMMIT | Una transacción registra el pago, sus aplicaciones y `PAYMENT_REGISTERED`, y se confirma. Después, sin transacción ni bloqueos abiertos, se genera el PDF y se envía el correo; su resultado se guarda en otra transacción (`receipt_email_status` SENT/FAILED + `RECEIPT_EMAIL_SENT`/`RECEIPT_EMAIL_FAILED`). | D8. Unidad | El administrador elige al residente; el backend determina su residencia vigente y la unidad. El cliente no puede enviar `unit_id`, `registered_at`, número de recibo, aplicaciones, saldo a favor ni estado (`extra="forbid"`: 422). |
| Residente que puede recibir pagos | Rol `RESIDENTE`, cuenta no eliminada, estado `ACTIVE` o `DISABLED` y residencia vigente (la misma definición de residente registrado de HU-006). | Snapshots | El pago guarda `resident_name_snapshot` y `unit_label_snapshot` (y su concepto, método, monto y fechas). El recibo y el resumen usan esos datos: no cambian si el residente cambia de nombre, teléfono, correo o unidad, o si la unidad se renumera. El correo se envía a la dirección actual del residente. |
| Estado del pago | Derivado de sus aplicaciones, nunca almacenado ni editable: `APPLIED` (Aplicado: todo aplicado), `PARTIALLY_APPLIED` (Aplicado parcialmente: una parte quedó como saldo a favor), `CREDIT` (Saldo a favor: nada aplicado). |

| Dinero | `DECIMAL(12,2)` en MySQL, `Decimal` en Python y texto decimal en la API (`"150000.00"`). Monto mayor que cero, hasta 2 decimales y como máximo $ 9.999.999.999,99. Se muestra como `$ 150.000,00` en la interfaz y en el PDF (siempre 2 decimales). En la interfaz se escribe sin puntos de miles; los centavos, con coma o punto. |
| Estado de cuenta (criterio 2.1) | Tras guardar, la respuesta y la confirmación incluyen el saldo de la unidad: pendiente (cargos no cubiertos) y a favor (partes no aplicadas de sus pagos), calculados en la misma transacción. El estado de cuenta completo es HU-011/HU-014. |
| Transacción y bloqueos (aprobado) | Orden **unidad primero**, el mismo de HU-013 y HU-019: bloque (S) → torre (S) → apartamento (X) → residencia vigente (S) → residente (S) → cargos pendientes (X, en orden FIFO). | Índices | Solo los usados por consultas reales: `charges(unit_id, due_date, created_at)` (FIFO y FK), `payments(resident_id, payment_date)`, `payments(unit_id)`, `payments(payment_date)`, `payments(registered_by_user_id)` (FK), `payment_allocations(payment_id, charge_id)` UNIQUE y `payment_allocations(charge_id)`. |
| Salvaguarda de HU-001 (aprobada) | La prueba de HU-001 prohibía cualquier ruta de escritura con la palabra `admin`, lo que chocaba con `POST /api/v1/admin/payments`. Se precisó sin debilitarla: ninguna ruta de escritura contiene `user`, `admins`, `administrator`, `register` ni `signup`; `admin` solo aparece como prefijo del área `/api/v1/admin/`; y toda escritura de esa área responde 401 sin sesión y 403 a un residente. |
| HU futuras | Base para HU-008 (historial del residente), HU-010 (pago electrónico simulado: otro `source`), HU-011 y HU-014 (estado de cuenta) y HU-012 (reportes). HU-004 no crea endpoints de residente. |

## HU-006 — Visualización de residentes registrados (detalle)

| Tema | Decisión |
|---|---|
| Alcance | Solo consulta, solo ADMINISTRADOR. No crea, edita ni elimina residentes (HU-015), ni toca invitaciones, activación, recuperación o unidades. |
| Extensión de diseño: residente registrado y estado (criterios 1 y 2.2) | El documento habla de "residentes registrados" y de su estado "activo o inactivo" sin definirlos sobre el modelo de datos. **Esta decisión no modifica la HU académica: solo precisa cómo se aplica al modelo existente.** Para el listado de HU-006, un **residente registrado** es una cuenta que cumple a la vez: rol `RESIDENTE`; cuenta no eliminada (`deleted_at` vacío); estado `ACTIVE` o `DISABLED`; y una relación residencial vigente (`resident_units` con `ended_at` vacío, creada al activar la cuenta en HU-019). El estado se presenta así: `ACTIVE` → "Activo" y `DISABLED` → "Inactivo" (la API expone `ACTIVE` / `INACTIVE`). **No se consideran residentes registrados**: las cuentas `PENDING_ACTIVATION` (invitadas que no han activado su cuenta), las residencias terminadas, las cuentas eliminadas y las cuentas de otro rol. Una persona que cambió de apartamento aparece una sola vez, con la residencia vigente. Hoy ningún flujo deshabilita residentes (llegará con HU-015), así que en la práctica todos aparecen como "Activo". |
| Endpoint | `GET /api/v1/admin/residents?page&page_size&search&status&sort_by&sort_order`, con `require_roles(ADMINISTRADOR)` (401 / 403, HU-018; clasificado en `ACCESS_POLICY`). Solo GET: sin CSRF. `Cache-Control: no-store` (datos personales). Los parámetros desconocidos (p. ej. `role`, `user_id`) se rechazan con 422. Respuesta: `{items, page, page_size, total, total_pages}`; cada residente: `id`, `full_name`, `document_number`, `phone`, `email`, `unit {id, label}`, `status`. Nunca hashes, tokens ni campos internos. |
| Paginación | En el servidor. `page` de 1 a 10 000 y `page_size` de 1 a 100 (la interfaz ofrece 10, 25 y 50); por defecto 1 y 10. Una página posterior a la última responde 200 con `items` vacío y los totales reales (la interfaz salta a la última página). |
| Búsqueda | Solo por nombre completo o número de documento, por fragmento (`LIKE '%…%'` con `%`, `_` y el carácter de escape tratados como literales), sin distinguir mayúsculas ni tildes (intercalación de la columna). Hasta 100 caracteres; espacios alrededor ignorados; vacía = sin búsqueda. No busca por correo, teléfono ni unidad. |
| Ordenamiento | Lista blanca `name`, `document`, `unit`, `phone`, `email`, `status` y `asc`/`desc`, traducida en el servicio a expresiones de SQLAlchemy (nunca texto del cliente en el SQL). `unit` ordena numéricamente por número de bloque, torre y apartamento (no por el texto del identificador). `document` ordena por longitud y luego por valor, así los documentos numéricos quedan en orden numérico. Teléfono y documento vacíos van al final en ambos sentidos. Desempate por `users.id` para que las páginas sean estables. |
| Consulta | Dos sentencias en MySQL: un `COUNT` y la página (`LIMIT`), con los mismos filtros y solo las columnas necesarias; nada se filtra, ordena ni pagina en Python o en el navegador. |
| Índices / migración | Sin migración. Las uniones usan claves primarias e índices existentes (`resident_units.user_id`, `units.tower_id`, `towers.block_id`); la búsqueda por fragmento (`%…%`) no podría usar un índice B-tree y el volumen de una copropiedad es pequeño. |
| Unidad | El identificador (`B1-TO2-APTO-104`) se construye con `app/core/unit_labels.unit_label` en cada consulta; no se almacena. |
| Actualización de la lista visible (criterio 4.1) | **No es una actualización push.** HU-006 no implementa WebSockets, SSE ni ninguna conexión persistente: el servidor no avisa al navegador de los cambios. La lista visible se mantiene al día **volviendo a consultar** la API (refetch, sin caché) cuando corresponde: al cambiar la búsqueda, el filtro, el orden o la página; al regresar a la vista o a la pestaña (`visibilitychange`, o `pageshow` desde el historial); y con la acción de recuperación "Reintentar". Cada consulta lee el estado actual de la base de datos, así que refleja las activaciones (HU-019), las renumeraciones de bloque, torre o apartamento (HU-013) y los cambios en las cuentas. Cuando HU-015 añada operaciones que modifiquen la información del residente, deberá invalidar o volver a consultar la lista tras cada operación. |
| Confirmación (criterio 4.2) | Pendiente de HU-015: la confirmación se produce después de modificar la información de un residente, y esa operación pertenece a HU-015. HU-006 no crea operaciones de modificación. |
| Frontend | Página `/admin/residents` (Astro SSR, protegida por el middleware de HU-018) con un controlador TypeScript puro (`src/lib/residents/residents-list.ts`, probado con `node --test`), sin React ni librerías nuevas, igual que el resto del proyecto. Las opciones se guardan en la URL. Búsqueda con espera de 300 ms; una respuesta antigua nunca reemplaza a una más reciente. 401 → `/login`; 403 → "No tienes permiso para ver los residentes."; otros errores → mensaje y "Reintentar". Las filas se construyen con `textContent` (sin HTML del servidor). En móviles la tabla se desplaza dentro de su tarjeta. |

## HU-018 — Control de acceso según rol (detalle)

| Tema | Decisión |
|---|---|
| Auditoría inicial | Se revisaron todas las rutas de la API (28), las dependencias, el middleware y las páginas. Los 19 endpoints de administración (HU-013, HU-003) ya usaban `require_roles(ADMINISTRADOR)`; los 8 públicos (login, logout, salud, HU-016, HU-019) no aceptan identidad ni rol del cliente; `GET /auth/session` devuelve solo los datos propios. **No había ningún endpoint privado sin autorización en el backend** ni endpoints de residente con identificadores (sin superficie IDOR). El middleware resiste variantes de ruta (`/%61dmin`, `//admin`, `/./admin`, `/x/../admin`, `/admin/index.html`). |
| Reutilización | Sin migración, sin tablas `roles`/`permissions`, sin endpoints nuevos y sin un segundo mecanismo: la sesión (HU-002), `get_current_auth` (401) y `require_roles(...)` (403) siguen siendo el único control. Solo dos roles: `ADMINISTRADOR` y `RESIDENTE`. |
| Política declarada | Cada ruta publicada (35 desde HU-005, que añadió las 4 rutas de `/admin/feedback` como ADMINISTRADOR; HU-004 añadió `GET`/`POST /admin/payments`; HU-006 añadió `GET /admin/residents`) tiene su nivel (público, cualquier rol autenticado, ADMINISTRADOR, RESIDENTE) en `ACCESS_POLICY` (`backend/tests/integration/test_access_control.py`); las pruebas lo comparan con las rutas reales y comprueban el comportamiento de cada una. Una ruta nueva sin clasificar hace fallar las pruebas. Es la matriz de [HU-018](historias-usuario/HU-018.md). |
| Rol en cada petición | El rol se lee de la base de datos en cada petición (cookie → sesión → usuario → estado → rol): un cambio de rol o de estado de la cuenta se aplica de inmediato a las sesiones abiertas. Nada enviado por el cliente (`role`, `user_role`, `user_id`, cabeceras, cookies) lo sustituye. |
| 401 / 403 | Sin el contrato cambiado: 401 `NOT_AUTHENTICATED` sin sesión válida (inexistente, mal formada, revocada, vencida o de una cuenta inactiva); 403 `FORBIDDEN` con sesión válida y otro rol; el 403 se decide antes de leer o validar el recurso, así que no revela si un identificador existe. Un JSON sintácticamente roto recibe 422 antes de la autenticación (comportamiento de FastAPI; no se ejecuta nada). |
| Administrador en funciones de residente | Política: 403 (`require_roles(RESIDENTE)`). Hoy no existe ningún endpoint exclusivo de residente; las HU del residente (HU-008, HU-009, HU-010, HU-014) los añadirán con esa dependencia y comprobando la propiedad del recurso desde la sesión. |
| Frontend | La decisión del middleware se extrajo a `frontend/src/lib/auth/page-access.ts` (función pura, probada con `node --test`, con el mismo comportamiento). Sin sesión → `/login`; otro rol → "Acceso no autorizado" (403, ahora también con `Cache-Control: no-store`), sin la página ni sus datos; el login lleva al área del rol; si la sesión no se puede comprobar → 503. Es solo una ayuda de navegación: la autorización real es la del backend. |
| Accesos denegados en la auditoría | No se registran en `audit_logs`: un 403 no cambia datos, se decide solo con la sesión y registrarlo permitiría llenar la tabla con peticiones repetidas. No se añadió ninguna acción de auditoría. |
